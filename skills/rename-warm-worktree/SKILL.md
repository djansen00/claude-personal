# Rename a Warm Worktree

## Overview

A warm area's slug is not one name — it is written into **ten** places. Renaming the
directory alone leaves nine of them stale, and almost all fail *silently*: the skill
symlinks dangle, the Terminal Keeper terminal cd's into a directory that no longer
exists, `omni_ports` reports *unknown area*, and the git worktree admin files still
point at the old path.

**It's mechanical — run the bundled script:**

```bash
~/.claude/skills/rename-warm-worktree/rename-warm-worktree.sh <old-slug> <new-slug>
```

**Always dry-run first** (it is free and prints every action):

```bash
~/.claude/skills/rename-warm-worktree/rename-warm-worktree.sh <old> <new> --dry-run
```

To rename only the VS Code terminal label, leaving everything on disk alone:

```bash
~/.claude/skills/rename-warm-worktree/rename-warm-worktree.sh --label-only <slug> <new-label>
```

## ⚠️ A live Claude session in the area — the two-phase rename

**The move itself does not strand anything.** Linux tracks a process's cwd by inode, so
`/proc/<pid>/cwd` follows a parent-directory rename (verified). Only bash's *cached*
`$PWD` string goes stale — cosmetic, fixed with `cd "$(pwd -P)"`. Do not believe the
folklore that every terminal must be closed first.

**One step genuinely conflicts: step 8.** A running `claude` is appending to the very
transcript directory that step moves. Whether that is harmless depends on whether Claude
Code holds the file open or re-opens it by path each turn — if by path, the next message
recreates the old-key directory and the conversation **splits across two dirs**. That
race exists no matter where the rename runs from, so running it *inside* the session does
not avoid it.

So when a live `claude` is detected in the area, the script refuses and points at the
two-phase flow:

```bash
# 1. rename everything except the history (safe with the session still running)
rename-warm-worktree.sh <old> <new> --skip-history

# 2. …later, once you close that session:
rename-warm-worktree.sh --history-only <old> <new>
```

Between the two phases the live session keeps working: its cwd follows the move, and it
keeps writing to the old-key transcript dir — which is exactly what phase 2 picks up.
`--history-only` refuses while a `claude` is still running in the area.

A live **dev stack** is a separate check: stop `~/start-omni-<old>.sh` first, because the
Ingest API takes its port as a launch-time `--urls` argument and cannot be re-pointed
without a restart.

## The ten places a slug lives

| # | Artifact | What the script does |
|---|---|---|
| 1 | `~/source/repos/<slug>/` | One `mv` of the whole area |
| 2 | Each repo's git worktree admin file | `git worktree repair` from inside each moved worktree |
| 3 | `feature/<slug>-wt` placeholder branch (per repo) | `git branch -m`, **skipped if it has an upstream** |
| 4 | `~/omni-ports.sh` table key | Re-keyed, **offset preserved** (see below) |
| 5 | `~/<slug>.sh` launcher | Renamed; only its `cd` line carries the slug |
| 6 | `~/start-omni-<slug>.sh` | Renamed + 8 targeted field rewrites |
| 7 | `~/reset-omni-<slug>.sh` | Renamed + 2 field rewrites |
| 8 | `~/source/repos/.vscode/sessions.json` (Terminal Keeper) | `name` + `cwd` rewritten via `jq --indent 4` |
| 9 | Area-root `CLAUDE.md`, `.claude/skills/*` symlinks | Regenerated by `omni-configure-area.sh` / `sync-omni-skills.sh` |
| 10 | `~/.claude/projects/<slugified-cwd>/` — Claude Code conversation history | Dirs moved to the new key + the `cwd` recorded inside each transcript rewritten |

Plus an eleventh that is not a slug but breaks anyway: each repo's gitignored
`current-work.json`, which stores **absolute** area paths.

## Non-obvious points (the judgment calls the script encodes)

| Point | Why it matters |
|---|---|
| **The port OFFSET is preserved; only the table KEY changes** | The area's actual port numbers are already baked into its gitignored `appsettings.Local.json` (Kestrel URLs **and CORS origins**), both `.env.development.local` files, and its generated `vite.config.local.mts`. Re-allocating a fresh offset on rename would invalidate all of them and quietly break the login gate. `~/omni-ports.sh` says as much in its own header: the table is explicit precisely so a rename doesn't renumber anything. |
| **`mv` + `worktree repair`, not `git worktree move` ×5** | The admin dirs live in the **main** checkout at `~/projects/omnibus` and don't move; what breaks is each admin dir's `gitdir` pointer back to the worktree. A single `mv` is one same-filesystem `rename(2)` — atomic and instant — and it carries the non-repo files (`CLAUDE.md`, the flattened `.code-workspace`, `.cc-keep-worktree`, `.claude/`) along for free. `git worktree move` would have to run once per repo and would leave all of those behind. `worktree repair` run *inside* a manually-moved worktree is git's own documented fix for exactly this. |
| **Targeted seds — never `s/<old>/<new>/g`** | A slug can be a domain word that legitimately appears throughout its own script. `start-omni-ingest.sh` is the live example: a blanket replace would rewrite every mention of the Ingest *service*. The script rewrites 8 named fields (header, port comment, `WORKTREE=`, four `*.log` paths, `TAG=`) and then **greps the result for residual mentions and prints them for you to eyeball** — so anything it missed is visible rather than silent. |
| **The Terminal Keeper entry is found by `cwd`, not by `name`** | A terminal's label is *allowed* to differ from the slug and two already do: `title-manager` → `titlemanager`, `CatalogManager` → `catalogmanager`. Matching on name would miss those entries entirely. |
| **A custom label survives the rename** | If the old terminal name equalled the old slug, it follows to the new slug. If it was deliberately different (the two above), it is **kept** and the script says so. Pass `--label <name>` to set it explicitly either way. |
| **Skill symlinks are absolute and all dangle after the move** | `~/source/repos/<slug>/.claude/skills/*` are absolute symlinks into two repos. Every one breaks. `~/sync-omni-skills.sh <new>` rebuilds them; the script calls it, and the verification block reports the dangling count so a failure is caught. |
| **`claude -c` history is keyed by cwd — this is the one you notice first** | `~/.claude/projects/<slugified-cwd>/` holds the conversation history, and the directory **name is the slugified absolute cwd** (both `/` and `.` become `-`). Rename the area and every history dir under it is orphaned, so `claude -c` silently starts a fresh conversation instead of continuing. An area can have **several** — one per cwd ever used in it (the area root, plus any repo subdirectory a terminal points at). `CatalogManager` had two: the root (3 transcripts) and the frontend subdir (2, in active daily use). The script moves each to the new key, rewrites the `cwd` field recorded inside every `.jsonl`, and keeps a **hardlink** backup under `~/.claude/rename-backups/` — instant and near-zero disk, and `sed -i` writes a new inode so the backup keeps the original bytes. |
| **The directory on disk is authoritative, and casing drifts** | Areas are not uniformly cased (`CatalogManager` vs `quickfix`), and the name you type is often the *terminal label* rather than the directory. The script resolves the old slug case-insensitively against `~/source/repos/` and reports what it picked. The home scripts drift independently of the directory — `CatalogManager` has lowercase `~/catalogmanager.sh` and `~/start-omni-catalogmanager.sh` but capitalized `~/reset-omni-CatalogManager.sh` — so they are found case-insensitively too, and every content sed carries the `I` flag. A rename normalizes all of it to the new slug. |
| **The launcher's `cd` may have no trailing slash** | `~/catalogmanager.sh` is `cd /…/CatalogManager|| exit 1`. A pattern anchored on a following `/` misses it silently. The sed anchors on a word boundary instead. |
| **A terminal's `cwd` is not necessarily the area root** | `catalogmanager`'s terminal points at `…/CatalogManager/Treeline.Clients.EdelweissComponents/` — it starts Claude inside the frontend repo. The script matches the area root as a **prefix** and rewrites only that, preserving the subpath, because the subdirectory is a deliberate choice: it is what `claude -c` keys off, so changing it silently switches which conversation resumes. |
| **`current-work.json` holds absolute paths** | `worktreeRoot`, `workspace`, `repositories[].path`, `sessionLog`, `specFile`, `planFile` — all absolute. It is gitignored, so no git operation fixes it. Left stale, the statusline and `/work-resume` point at a directory that no longer exists (the same class of trap documented in `reset-warm-worktree`). The script rewrites these in place and leaves a `.bak-rename` beside each. |
| **Session logs and docs are reported, not rewritten** | `work/*.md` and `docs/sessions/*.md` mention the old path too, but they are **historical records** of where the work happened. Rewriting history would be a lie; the script lists them and moves on. The live session's log still resolves, because the `sessionLog` *pointer* in the state file is rewritten and the file itself moves with the area. |
| **State files are found without a depth cap** | The deepest real one lives at `<area>/Treeline.Workspaces/Data/.claude/work-sessions/state/current-work.json`. An earlier `-maxdepth 6` sat exactly at that depth — one more level of nesting and it would have missed silently. The `-path` glob scopes the search; `node_modules` is pruned. |
| **A pushed placeholder branch is left alone** | `feature/<slug>-wt` is meant to be local-only. If it has an upstream it was pushed, and renaming it locally would orphan the remote ref. The script warns and skips. |

## An active session is the normal case

Renaming an area with live work in it is the expected use, not an edge case, and it is the
main reason to rename rather than recreate. What happens to it:

- **Branches and uncommitted work** — untouched. The `mv` carries the tree byte for byte;
  only the `feature/<slug>-wt` placeholder is renamed.
- **Every `current-work.json`** — rewritten. All path-bearing fields (`originatingCwd`,
  `worktreeRoot`, `workspace`, `repositories[].path`, `sessionLog`, `specFile`, `planFile`)
  share the one area-root prefix, so a prefix substitution catches all of them. A
  `.bak-rename` is left beside each.
- **The conversation itself** — preserved, via the history step above. Without it, `/work-resume`
  would find its state intact while `claude -c` started from nothing.
- **Verification** — after rewriting, the script asserts that no state file still names the old
  area and that every `sessionLog`/`specFile`/`planFile` pointer resolves on disk.

What it will *not* do is rename an area out from under a **running** session: if a process has
its cwd inside the area, it refuses.

## What the script does NOT do

- **Allocate a new port block.** The rename is name-only by design — see the offset note above.
- **Reset or clean the repos.** In-flight branches and uncommitted work ride along untouched.
  Run `~/reset-omni-<new>.sh` afterwards if you also want the between-sessions reset
  (see `reset-warm-worktree`).
- **Rename an area that doesn't exist yet.** To create one, use `create-warm-worktree`.

## After it finishes

The script prints a verification block: per-repo branch + worktree-link health, the area
root, whether the old path is gone, whether `CLAUDE.md` was regenerated for the new slug,
the linked/dangling skill-symlink counts, the port-table line, the three home scripts, the
Terminal Keeper name, and any leftover `~/*<old>*` files.

Then:
1. **Reload the VS Code window** — Terminal Keeper only re-reads `sessions.json` on activation.
2. Launch the area with `~/<new>.sh`.
3. If `node_modules` is stale (long branch jump), `npm install` in
   `Treeline.Clients.EdelweissComponents` before starting the stack — same trap
   `reset-warm-worktree` documents.

## Recovery if it fails mid-run

The `mv` is atomic, so the area is either fully at the old path or fully at the new one.
If the move succeeded but a later step failed, **re-running is not the fix** (the old path
is gone). Finish by hand from the table above — the steps are independent. If only the
history step is outstanding, `--history-only <old> <new>` finishes it. The step that looks
scariest is the cheapest:

```bash
git -C ~/source/repos/<new>/<repo> worktree repair   # idempotent, safe to re-run
~/sync-omni-skills.sh <new>
~/omni-configure-area.sh <new>
```

## Common mistakes

- **Renaming the directory with plain `mv` and stopping there.** Eight of the nine places
  stay stale and every one of them fails quietly. This is the reason the skill exists.
- **Believing the rename strands processes in the area.** It does not — cwd follows the
  inode. Only bash's cached `$PWD` goes stale. The real constraint is narrower: step 8 vs.
  a live `claude`, which the two-phase flow above handles.
- **Reaching for `create-warm-worktree` + delete instead.** That re-runs a multi-minute
  `npm install` (~1.8 GB), allocates a *new* port block, and throws away the area's
  branches and in-flight state. A rename is seconds and keeps all of it.
- **Assuming the Terminal Keeper name must equal the slug.** It doesn't, and two areas
  already prove it. Use `--label` when you want them to differ, or `--label-only` when the
  label is the only thing you actually wanted to change.
- **Changing the port offset "while you're in there."** It invalidates the CORS origins
  and `.env` values already written to disk.
